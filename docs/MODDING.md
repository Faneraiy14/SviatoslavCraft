# Моди Voxelin

Моди - звичайні jar-файли в теці `mods/` (поруч із `saves/`). Завантажувач модів - частина самої гри: окремо нічого не ставиться, «ванільної» і «модової» версії нема. Є jar-и в `mods/` - гра їх завантажує, нема - просто йде далі.

Це власне API Voxelin, а не FL Loader: моди для Minecraft на FL Loader у Voxelin не працюють, і навпаки (різні ігри - різні блоки, істоти й світ).
Ванільний вміст гри (`voxelin.content.VanillaContent`) реєструється через **той самий API**, що й моди.

## Мінімальний мод
1. Збери гру: `./build.sh` у корені - з'явиться `voxelin-api.jar` (лише пакет `voxelin.api`).
2. Клас, що реалізує `voxelin.api.VoxelinMod` і в `init(ModContext)` реєструє блоки, команди, слухачі подій.
3. У `META-INF/MANIFEST.MF` jar-а:
   ```
   Voxelin-Mod: com.example.MyMod
   Voxelin-Mod-Id: mymod
   Voxelin-Api: 2
   Voxelin-Api-Requires: events.chat, service.config   (необов'язково)
   ```
   `Voxelin-Mod-Id` - малі латинські літери, цифри, `_` (до 32). Це префікс усіх блоків мода: `mymod:ruby`.
4. Приклад - `examples/hello-mod` (`bash build.sh` -> `hello-mod.jar`).

## Що доступно (API версії 2)
- **Блоки** (`ctx.registries().block(назва, BlockSettings)`): колір, текстури граней, суцільність, прозорість, напівпрозорість, рідина, світло, твердість. Блоки - це дані, не код.
- **Істоти** (`ctx.registries().mob(назва, MobSettings)`): здоров'я, розмір, поведінка (мирна/ворожа/нейтральна/вартова), удар, модель з коробок, що падає. Стрілець: `.ranged(відстань, пауза_с, швидкість_стріли)` - тримається за 6..відстань блоків і стріляє, поки бачить гравця (як скелет).
  - Модель: `.part(...)` - тіло, `.head(...)` - голова з обличчям (дивиться на гравця до 60°), `.onHead()` - остання частина рухається з головою (роги, капелюх), `.legPart` / `.armPart` / `.wingPart` - ноги, руки (змахують при ударі), крила. `.pattern("fur")` - візерунок текстури останньої частини: fur, skin, bone, cloth, leather, scale, shell, stone, glow (світиться в темряві). `.face(0xRRGGBB)` - колір очей.
  - Свої текстури частин: `textures/<мод>/mobs/<моб>_<номер частини>.png` (номер - порядок частини з 0), обличчя - `<моб>_<номер>_face.png`. Будь-який розмір, масштабується до 16x16. Без файла текстура генерується з кольору й візерунка.
  - Наземні істоти шукають шлях самі (обходять стіни, ходять сходами, не падають з урвищ глибше 3 блоків).
- **Події** (`ctx.events().on(Клас, слухач)`): `TickEvent` (20/с), `BlockChangeEvent` (можна `cancel()`), `ChunkGeneratedEvent` (дописати руду/структури в новий чанк - викликається з фонового потоку), `WorldOpenEvent`.
- **Команди** (`ctx.commands().register(назва, використання, права, обробник)`).
- **Світ** (`WorldAccess`): `getBlock`, `setBlock(Source, ...)`. Усі зміни йдуть від імені джерела (`Source`) з правами й лімітом змін за тік.

## Нове в API (гра 1.1.0, API версії 2 - старі моди працюють)
- **Можливості:** `ctx.has("events.chat")` - чи є в грі ця частина API (перелік - `VoxelinApi.FEATURES`). Перевір перед тим, як чіпати нові класи, - тоді мод працює й на старішій грі, просто без цієї функції.
- **Вимоги в маніфесті:** `Voxelin-Api-Requires: events.chat, service.config` - якщо гра чогось не має, мод не завантажується, а в списку модів написано, чого бракує: «онови гру» (замість падіння посеред гри).
- **Сервіси:** `ctx.api(Інтерфейс.class)` - додаткові частини API; `null` - у цій версії гри такого нема.
  - `ModConfig` (`service.config`) - налаштування мода у файлі `config/<id мода>.properties`: `getInt("ruby.veins", 12)` повертає значення або типове й записує його у файл після `save()`, щоб гравець бачив, що можна змінити.
- **Нові події:** `MobDeathEvent` (вид, бос чи ні, місце; один раз на істоту), `PlayerJoinEvent` / `PlayerLeaveEvent` (сам гравець, гості гри по мережі, сервер без вікна; причина виходу), `ChatEvent` (повідомлення до того, як його побачать інші; `cancel()` - не пропустити).
- Приклад `examples/hello-mod` користується `ModConfig`, `ctx.has` і `MobDeathEvent`.

## Як росте API (правила, щоб моди не ламались)
Головна проблема модів для Minecraft - API там не задумане: моди латають код гри, і кожне оновлення гри їх ламає. У Voxelin API - частина ядра від першого дня, і росте за правилами:
1. **Нова частина API - новий тип, а не зміна старого.** Подія - новий клас у `voxelin.api.event` + один виклик `events.post(...)` у ядрі. Сервіс - новий інтерфейс у `voxelin.api` + один рядок `services.provide(...)` у `loader/Game`. Новий метод в інтерфейсі - лише `default`. `ModContext` і ядро при цьому не переписуються.
2. **Кожна нова частина - рядок у `VoxelinApi.FEATURES`.** Моди дізнаються про неї через `ctx.has` / `Voxelin-Api-Requires`.
3. **Нічого не видаляється й не змінюється без підняття `VoxelinApi.VERSION`.** Це стереже тест `VoxelinApiTest`: він звіряє всі публічні класи, поля й методи `voxelin.api` зі знімком `docs/api-signatures.txt` і падає, якщо щось зникло або змінилось. Нове теж треба свідомо внести у знімок: `./build.sh api-snapshot`.
4. **Ванільний вміст гри користується тим самим API**, тож API не відстає від гри: усе, що вміє гра, мод теж може.

## Скрипти NyxilumLang (без збирання jar)
Простіший шлях: скрипт мовою NyxilumLang (`nx`). Потрібен встановлений `nx` (у `PATH` або шлях у змінній `VOXELIN_NX`).
- Тека `scripts/` поруч із `mods/`; кожен скрипт - `scripts/<назва>/main.nx` (назва - малі латинські літери, цифри, `_`). Гра запускає їх з першим тіком світу.
- Перший рядок - `import "../voxelin.nx"` (помічник; гра сама кладе його в `scripts/` і оновлює - не правь його), останній у `main()` - `vxRun()`.
- **Збереження будь-якого `.nx` у теці скрипта перезапускає його** - зручно писати в зовнішньому редакторі (NyxilumIDE). Впалий скрипт теж запуститься після виправлення.
- Приклад - `examples/hello-script/main.nx`.

Що є в помічнику:
- `say(текст)` - повідомлення гравцеві; `log(текст)` - у лог гри (так само звичайний `print`).
- `setBlock(x, y, z, "bricks")` (без `:` - це `voxelin:...`), `getBlock(x, y, z)` -> назва або `null` (чанк не завантажено).
- `run("/fill ...")` - будь-яка команда гри від імені скрипта (права як у команд будування), повертає масив рядків відповіді.
- `player()` -> мапа `x, y, z` (ноги), `health`, `alive`, `creative`, `dimension`; `worldTime()` -> `time, day, dayTicks`.
- `command("назва", "підказка", обробник)` - своя команда `/назва`; обробник отримує мапу `args` (масив), `x, y, z` (де гравець), `by`.
- `on(подія, обробник)`: `"tick"` (20/с), `"second"`, `"block"` (гравець змінив блок: `x y z old new by`; скасувати не можна), `"world"` (інший вимір), `"stop"` (скрипт зупиняють - час зберегти дані).
- З наступної версії після 1.1.0 - ті самі події, що й у jar-модів: `"join"` / `"leave"` (`name`, `guest`, `reason`), `"mob_death"` (`mob`, `boss`, `x y z`), `"chat"` (`name`, `text`, `guest`; скасувати зі скрипта не можна - він в окремому процесі).

Пісочниця й ліміти (скрипти можна брати в інших людей - на відміну від jar-модів):
- окремий процес `nx` з `NX_SANDBOX=1`: файли - лише у власній теці скрипта, без мережі, запуску програм і змінних середовища;
- не більше 256 змін блоків за тік (решта чекає наступних тіків), обробка операцій усіх скриптів - до 4 мс на тік;
- скрипт, що не відповідає 5 с ігрового часу (нескінченний цикл в обробнику) або займає понад 512 МБ пам'яті (Linux), зупиняється; гравець бачить причину.
- `/script list`, `/script reload <назва|all>`, `/script stop <назва>`, `/script log <назва>` (останні рядки виводу й помилки).

### Скрипти світу
Скрипт можна покласти не в загальну `scripts/`, а в теку світу: `saves/<світ>/scripts/<назва>/main.nx`. Він працює лише в цьому світі й **їде разом зі світом**, коли світ експортують у `.vxworld` (меню світів -> ЕКСПОРТ / ІМПОРТ, тека `share/`). За однакової назви скрипт світу перемагає загальний.

У **грі по мережі** скрипти й моди працюють лише в хоста. Блоки, які ламають і ставлять гості, приходять у ті самі події (`placed`/`broken`, `BlockChangeEvent`) від гравця з ім'ям гостя (без прав оператора), тож скрипт може на них відповісти або скасувати.

### Вікно коду в грі (K)
Невелике вікно коду з консоллю - щоб правити скрипт, не виходячи зі світу (повна IDE - це NyxilumIDE зовні).
- Ліворуч - скрипти з `scripts/` (зелена точка - працює, сіра - зупинений, червона - впав або зупинений грою); **+ НОВИЙ** створює `scripts/<назва>/main.nx` із прикладом команди `/<назва>` і одразу запускає.
- Посередині - редактор із підсвіткою; унизу - консоль скрипта (його `print`/`log` і помилки) та стан.
- **Ctrl+S** - зберегти й перезапустити; **ЗУПИНИТИ** - як `/script stop`. Esc - закрити (з незбереженими змінами - спершу попередження).
- **БЛОКИ** (або «+ НОВИЙ» -> «БЛОКАМИ») - редактор блоків як у Scratch, без друку коду (див. нижче).
- Клавіші: Enter тримає відступ (+4 після `{`), Tab / Shift+Tab - відступ рядків, Ctrl+Z / Ctrl+Y, Ctrl+A/C/X/V, Ctrl+/ - коментар, Ctrl+D - дублювати рядок, Ctrl+стрілки - по словах, коліщатко й мишка - прокрутка, курсор, виділення.

Протокол для інших мов (помічник робить це сам): гра пише в stdin по JSON-рядку `{"ev":"start|tick|second|block|world|command|reply|ping|error",...}`, скрипт друкує в stdout `{"op":"say|log|setBlock|getBlock|run|player|time|command|subscribe|pong|ready",...}`. Запит з `"rid"` отримує `{"ev":"reply","rid":...}`. На `ping` треба відповісти `{"op":"pong","n":...}`. Кінець stdin - гру закрито.

## Правила й гарантії
- Версія API (`Voxelin-Api`) росте **лише** коли щось, на що вже спираються моди, зламано. Нові методи її не міняють - старі моди працюють далі.
- Мод з новішим API, без потрібних рядків маніфесту або з винятком у `init()` пропускається з повідомленням у лог - гра запускається все одно.
- Мод може реєструвати лише блоки зі своїм префіксом.
- Слухач події, що кидає виняток 3 рази поспіль, вимикається.
- У файлах світу блоки зберігаються за **назвами** (палітра в `voxelin.world`). Додавання/видалення модів не псує світ: блок, чийого мода нема, показується як `voxelin:unknown`.
- Моди виконуються з повними правами Java, як у Minecraft. Став лише моди, яким довіряєш.

### Блоки як у Scratch
Програма складається з блоків і зберігається в `scripts/<назва>/blocks.json`; поруч генерується справжній `main.nx`, який видно праворуч у редакторі - так видно, у що перетворюється кожен блок.
- **Події** (жовті «шапки»): коли скрипт запускається, коли гравець пише `/назва`, кожну секунду, коли гравець ставить / ламає блок (`*` - будь-який).
- **Дії**: сказати, поставити блок, заповнити область, будь-яка команда.
- **Керування**: повторити N разів (лічильники `i`, `j`, `k` - до 3 вкладень), якщо на позиції є блок, з шансом N %.
- **Змінні**: `=`, `+=`, якщо (порівняння `= ≠ < > ≤ ≥`).
- Числа - цілі або вирази з `+ - *`: `i*2`, `arg+1` (`arg` - перше число після команди), назви змінних. У тексті `{назва}` підставляє значення.
- Позиції - зсув від ніг гравця (у подіях блоку - від самого блоку): x - схід, y - вгору, z - південь.
- Клік у палітрі вставляє блок під вибраний (в обгортку - всередину); `^`/`v` (Ctrl+стрілки) переносять, зокрема всередину обгорток і назовні; КОПІЯ, ВИДАЛИТИ (Delete). До 500 блоків.
- Щоб перейти на код - видали `blocks.json` (інакше наступне збереження блоків перепише `main.nx`).
